# Standalone release validation — October 2, 2026

The 0.2.0 distribution implements five bounded execution policies and required pip-installed CPU Laya routing. This report describes engineering checks and small live samples, not general answer-quality or performance results.

Validation used Python 3.12 on macOS ARM64. The standalone suite passed (95 tests). The opt-in socket suite passed (11 tests): one ordinary OpenAI SDK check, nine actual curl commands from [the flagship document](flagship-curl-cases.md), and the benchmark CLI over real HTTP. These socket tests are excluded from the default run. Neither suite requires model weights or an external service; decision fixtures cover deterministic behavior. CI additionally declares Python 3.11–3.13; those remote CI runs have not been observed in this work session.

Checks cover ordinary OpenAI SDK model discovery/completions/streaming, role preservation, output-limit spelling, JSON Schema buffering/validation, function tool forwarding, parameter rejection, authentication, upstream error sanitization, missing/truncated/invalid evidence, immutable UTF-8 span validation, full submitted partition coverage, context/resource reservations, deadline/client-disconnect cancellation, post-commit stream failures, and spawned CPU-decision worker cancellation/reaping. Source input beyond the configured worker admission window is exercised with a deterministic backend fixture. This establishes runtime bounds/coverage plumbing, not extraction recall or a physical model's maximum usable context.

The curl document supplies exact payloads and contracts for direct policy answers, schema-constrained incident JSON, evidence mapping, batching, verification, focused retrieval, SSE, named caller-tool handoff, and an unsupported-choice error with zero backend calls. Tests replay these payloads through ASGI and run documented curl argv against real local Uvicorn servers with a deterministic physical HTTP backend. Generated/repository configurations include fixed aliases for all five policies. Additional tests reject missing batch partitions, cross-partition quotes, invalid verifier verdicts/IDs, unsafe decision probabilities, truncated decisions, disallowed choices, and budget violations; active selection happens before SSE commitment.

Before the multi-policy extension, the original six flagship requests passed live smoke checks through Prism to the existing Docker Model Runner endpoint for `ai/gemma4:E2B`: direct policy answer, schema-valid incident JSON, evidence synthesis, SSE, named tool-call handoff, and the expected HTTP 400 rejection. Streaming checks accept a valid opening `content: null` delta, preserve stable public IDs, and verify the usage-only final chunk and `[DONE]`. No application tool was executed.

The evidence-map sample used three short synthetic deployment-policy documents. Three extraction calls produced validated quotes; one synthesis call returned an answer describing approval, retrospective review, and rollback qualifications. Runtime coverage listed all three required partitions as validated, and the trace recorded four backend calls. The extractor prompt now uses a valid empty result example and clarifies that workers inspect their own partition; runtime checks still reject unresolved needs or incomplete evidence. This is a functional multi-call smoke test, not a long-context recall benchmark or evidence of equivalence to a stronger model. The Muse endpoint in the registry was unreachable, so no Muse or stronger-model comparison is claimed.

Live output was sensitive to generation budgets: a 32-token direct trial and a 1024-token evidence-synthesis trial returned empty content with `finish_reason=length` after reasoning consumed the budget. The documented evidence request now uses the default public cap of 2048 tokens; the SSE sample uses 1024. Prism preserves truncation and does not substitute reasoning text as the final answer. These successful smoke checks do not guarantee completion within those budgets for other models or runs.

Laya 0.3.23 was installed from PyPI and its real `convaiinnovations/laya-typed-decisions` checkpoint prepared in a spawned CPU process. Initial preparation took 11.79 seconds including download; a four-policy inference took 209 ms, returned option probability 0.3434, and correctly abstained under the 0.7 threshold. Full HTTP routing through the real checkpoint and Gemma took about 511 ms for the decision, proposed direct at 0.3493, and used the rules fallback. Neither decision was encoder-truncated. The checkpoint revision was `1a793eb568e6718f15941d08f85432581df534e3`, now pinned in shipped JSON defaults. Laya warns about clamping an uncalibrated shipped temperature entry; no policy-quality calibration is claimed. Process cancellation/reaping is covered with a deterministic model stub. The parent ASGI process keeps ML imports in the child.

Wheel and source distribution builds succeeded using the installed build backend (`--no-isolation`), and `twine check` accepted both artifacts. Laya is a base dependency and `dev` is the only extra. Only the `prism` namespace and console command are packaged. JSON defaults, the benchmark JSONL suite, typing marker, and MIT license are included; no provider-plugin registrations, removed package files, classifier constraints, model weights, caches, traces, or benchmark results are shipped. The source distribution includes policy/curl documentation and tests. Core metadata is pinned to version 2.4 for release-tool compatibility.

A clean temporary environment installed the wheel through pip with all dependencies, resolving Laya 0.3.24 and Torch 2.14.1. `pip check` passed. Outside the checkout, version/help, JSON initialization/validation, and the policy catalog worked; removed namespaces were absent, and help/configuration did not import Torch. The installed package prepared the real CPU checkpoint and served live HTTP requests. Tests also verify that unavailable checkpoint preparation prevents service startup and that `off` is rejected.

The packaged six-case reference benchmark was run twice against the configured Gemma endpoint with one measured repetition and no warmup. Direct execution completed 6/6 requests in each run, with a mean reference score of 0.917 and mean latency of 6.63/6.59 seconds. Forced evidence mapping completed 2/6 requests, scored 0.250, and averaged 14.54/14.35 seconds. Four requests failed with `incomplete_evidence`; their quality scores remain zero. The policy-revision case returned the correct retention period but used `Revision 2026-10` instead of the reference string `2026-10`, losing one exact-field check on both routes. This metric includes literal representation requirements and is not a semantic answer-quality judge.

The baseline recorded six physical calls per run. The candidate recorded 14, including interrupted worker work; three candidate calls had unknown provider usage. No prices are configured for these local models, so monetary cost remains unknown. Both run folders and an offline comparison were saved under `benchmark-results/`; the comparison accepted identical workload hashes and settings. These are small functional benchmark samples, not evidence of an orchestration speed/quality advantage or reliable long-context performance. See [benchmark instructions](benchmarking.md) to repeat the workload and declare actual pricing.

With required Laya startup, a two-case, one-repetition/no-warmup benchmark saved to `benchmark-results/gemma-batched-20261002`. Direct and batched mapping each completed 2/2; direct scored 1.000 at mean 6.08 seconds, batching scored 0.875 at 16.76 seconds. Calls were two versus four. Cost remains unknown. Separately, the longer three-document live smoke hit the 1024-token batched extractor output cap; verification rejected an interpretation/record check after six calls and correctly withheld synthesis. Focused retrieval and automatic routing completed in one physical call. Those failures remain in `benchmark-results/laya-policies-live-20261002/smoke.json`. Batching's shipped worker cap is now 2048 to accommodate multiple results, including reasoning; a larger cap does not guarantee completion. These small samples show operational behavior, without evidence of a speed/quality advantage.

The final installed wheel's short batched curl example completed in two calls and its focused retrieval example completed in one. Verification rejected a verdict/record check after five calls and withheld synthesis. Automatic routing used direct after Laya abstained at probability 0.2904; this first HTTP decision took 2.44 seconds with the clean environment's runtime. Results are in `benchmark-results/laya-policies-live-20261002-final/smoke.json`. Repeating the two-case benchmark after the output-budget and prompt changes saved `benchmark-results/gemma-batched-final-20261002`: direct completed 2/2, scored 1.000, and averaged 6.87 seconds; batching failed both quote/evidence checks, scored zero, and averaged 9.74 seconds including failures. The original and final runs remain separate, with an offline comparison in `benchmark-results/gemma-batched-before-after-20261002`. The comparison accepts identical workload hashes/settings; prompt/config/runtime differences and small-sample variation limit causal interpretation. Strict failures remain in quality denominators. No calibration or performance advantage is established.

Before publishing, configure PyPI project ownership/Trusted Publishing and run the manual release workflow on the reviewed revision. Before making workload-level accuracy, latency, price, or virtual-context claims, run paired evaluations with appropriate ground truth, backend tokenizers, pinned checkpoints, calibrated routing evidence, and real deployment limits.
